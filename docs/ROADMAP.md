# Roadmap

План от 2026-11-10. Работа небольшими итерациями; без календарных обещаний до первой сборки и native spike. Реализация требует следующего задания владельца. Этап 4 необязателен и не блокирует личный release.

## Phase 0 — Research & Architecture

**Цель:** отделить подтверждённые данные от рисков и выбрать простой путь.

**Задачи:** осмотреть каталог, создать девять документов, проверить официальные API/тарифы, зафиксировать устройство и реальные ответы, минимальный набор permissions и путь сборки без обязательной Studio.

**Зависимости:** исходный промт, официальные документы, сведения владельца. Уже получены A12/Android 12/Anor SIM 2, USSD-сумма и один SMS ULTRA. Нужны точный model code/One UI, sender и время SMS, подтверждение семантики интернета.

**Готовность:** документы согласованы, неизвестные перечислены, приложение и зависимости не создавались. Документальная часть завершена; device feasibility не проверена и перенесена в 2.1.

**Риски/проверка:** документация API не доказывает поведение оператора; каждый пункт device matrix остаётся отмеченным как непроверенный. Проверка сейчас — чтение документов, ссылки и согласованность контрактов.

## Phase 1 — Окружение и UI MVP

**Цель:** самостоятельный локальный Dashboard без ложных операторских данных.

**Итерации:**

1. После разрешения выбрать совместимый Expo SDK/RN/Node/JDK, minSdk/compileSdk, проверить окружение; найти либо установить нужные JDK и CLI Android SDK, проверить `adb devices`. GitHub/Git подключить в согласованном владельцем репозитории, не трогая служебные каталоги среды.
2. Создать минимальный TypeScript Expo-проект и development build; проверить запуск на A12. Зависимости добавлять только под текущую задачу.
3. Dashboard + Settings: empty/loading/error/success и обозначенный demo mode; реальные cache не заполнять mock-значениями.
4. Каталог ULTRA/LITE, ручной выбор, store, validated storage/hydration, timestamps и сброс данных.

**Зависимости:** разрешение реализации, место под SDK/caches, телефон/USB, совместимость SDK с Android 12.

**Готовность:** экран запускается на A12, работает без IP-сети и Metro в пробной release-сборке, перезапуск сохраняет snapshot, неизвестное не становится нулём, mock не смешивается с cache. Permissions не требуются для UI/импорта.

**Риски:** время toolchain и build, Java 25 может не подойти, SDK не найден в текущем PATH. **Проверка:** typecheck/lint по будущим scripts, ручной UI review с крупным шрифтом, содержательные tests store merge/hydration при их появлении. Учебная задача: написать selector процента с unknown/over-limit случаями.

## Phase 2 — USSD Integration

**Цель:** доказать либо опровергнуть получение баланса программно на целевом телефоне.

**Итерации:**

1. Узкий Kotlin spike: permissions, список подписок, Anor SIM 2, `sendUssdRequest('*100#')`, безопасный callback. До дизайна production parser сравнить реальный callback с системным ответом.
2. Typed native facade, один pending request, идентификаторы/timeout/errors, обработка позднего ответа и смены контекста.
3. Parser подтверждённого ответа `Тавозуни Шумо: 0.05TJS.`; точный разбор денег; интеграция refreshBalance и persistence.
4. ACTION_DIAL fallback и понятные инструкции без ложного «Баланс обновлён». Ручной ввод суммы добавлять, если нужен сокращённый MVP, после согласования поведения.

**Зависимости:** этап 1, реальная Anor SIM, CALL_PHONE/READ_PHONE_STATE с согласия владельца.

**Готовность:** протокол device matrix фиксирует результат для A12, правильную SIM и сумму, отказ/отзыв permissions, timeout/repeat/late callback не портят cache. Если native USSD не работает — честный documented blocker именно этой функции, работа над импортом может продолжаться.

**Риски:** OEM/network callback, неполное управление modem lifecycle, разные SIM/default routes. **Проверка:** реальные вызовы только по действию владельца, tests parser/operation state, никакой «проверки USSD» на одном mock. Учебная задача: разобрать Kotlin callback → Result и объяснить exactly-once completion.

## Phase 3 — SMS Parser и ручной импорт

**Цель:** реальные пакеты без доступа к истории SMS.

**Итерации:**

1. Подтвердить дневной смысл `Интернети бокимонда`, получить sender/time и дополнительные варианты (особенно LITE). Обезличить fixtures, отделить от mock.
2. Чистый parser текущего образца: блок ULTRA и отдельный «Стоп платный интернет трафик», число/единицы/дата, unknown/partial/ambiguous результаты.
3. Форма вставки, preview/подтверждение, предупреждения о неизвестной давности и SIM, commit только распознанных полей.
4. Отдельные timestamps, tariff mismatch, повторный/старый импорт и проверка контекста. Refresh All связывает USSD и предложение импорта, не объявляет автоматический SMS успех.

**Зависимости:** контракты/хранилище этапа 1; может идти независимо от успеха этапа 2. Один реальный ULTRA SMS уже есть, production-покрытие LITE ещё не подтверждено.

**Готовность:** на предоставленном образце: 29938.09 МБ, 35000 МБ ночью, 1000 минут, 50 SMS; expiry 10.12.2026 18:48:07 не заменяется бессрочностью услуги. Приветствие не сохраняется; нет SMS permissions. Неподтверждённая семантика имеет warning, не выдаётся за факт.

**Риски:** формат/локаль, бонусы, старые SMS, ambiguity expiry и timezone. **Проверка:** Jest на обезличенных реальных samples; синтетические негативные cases (дубликаты, неизвестные units, whitespace, oversize, missing fields) явно обозначены. Проверить ручной импорт на A12 и восстановление после restart. Учебная задача: написать tests, отличающие expiry основного пакета от unlimited услуги.

## Phase 4 — Automation, необязательный

**Цель:** оценить полезность автоматического получения новых SMS для конкретного пути установки.

**Задачи:** device spike RECEIVE_SMS/installer restrictions; согласие; allowlist sender и SIM; multipart/deduplication; lifecycle, force-stop и background; отдельный ADR о native persistence/очереди. READ_SMS не нужен просто для нового сообщения. Notification listener оценивать отдельно, не подключать автоматически.

**Зависимости:** работающий этап 3, новые разрешение и scope, проверка правил распространения. **Готовность:** либо доказанный opt-in путь с сохраняющимся manual fallback, либо документированное решение отказаться. Внедрение не обязательно.

**Риски:** hard-restricted permissions, Play policy, изменяющиеся уведомления, killed JS process, ложная привязка SMS к запросу. **Проверка:** реальная установка APK тем же способом, что у владельца/друга, grant/deny/revoke, restart/force-stop и контроль сохранения только данных Anor. Не обещать фоновую доставку после force-stop. Учебная задача: составить протокол жизненного цикла receiver без реализации лишнего background framework.

## Phase 5 — Polish и личный release

**Цель:** стабильный небольшой APK для владельца и, при желании, друзей.

**Задачи:** UI states, доступность/TalkBack, большой шрифт, performance на release, окончательные backup rules/manifest, отсутствие raw логов/analytics/upload, очистка cache, signing и инструкции установки/обновления. Хранить ключ отдельно, не публиковать автоматически. Решить подтверждённые units/timezone или оставить явно честное отображение МБ/локального операторского времени.

**Зависимости:** этапы 1–3 либо явно принятый сокращённый MVP; этап 4 не требуется.

**Готовность:** подписанный release APK со встроенным JS, работает без Metro, данные сохраняются, нет лишних permissions, update тем же ключом не теряет данные. Поддержка телефона друга утверждается только после отдельной проверки на нём.

**Риски/проверка:** ключ подписи, неподтверждённые модели, backup OEM и сетевые зависимости. Пройти PRD acceptance и Android matrix, измерить целевой cold start, проверить merged manifest и отсутствие сетевой передачи пользовательских данных. Не повторять все проверки после косметики без причины, но пройти release-critical пункты на итоговом APK.

## Ближайший шаг после документации

Дождаться следующего задания владельца. Разумный первый результат — настроенный CLI toolchain и пустой development build на A12. Пока не запускать установки, генераторы приложения и native-запросы.
